# PRD Convert Web — local Markdown increment

_October 28, 2026. Implemented in the repository; not deployed or published. Decision: PRD-048._

The existing web app now serves PRD Convert at `/convert/`, or `<hosting-base>/convert/`. Choose Markdown/HTML with optional supporting raster files, or a bounded CBZ archive containing its own pages; convert locally, review the actual report, download a valid PRD and open those exact generated bytes in the existing Viewer. The original Markdown increment is described below, with subsequent HTML and CBZ policies linked at the end. It is a focused ingestion surface rather than a Studio editor or a new renderer.

## Execution and package boundaries

The Node entry of `@eonhive/prd-converter` retains its public APIs, filesystem limits, six adapters and CLI behavior. A new `@eonhive/prd-converter/browser` export accepts an explicit `ImportSource` byte snapshot, selected resources and existing conversion settings through `convertMarkdownInBrowser`. That original export registers only the existing Markdown adapter. The October 29 `convertInBrowser` addition also supports static HTML with lazy adapter/parser loading; see the continuation below. No Node imports, Buffer polyfill, PDF/native canvas, optional HTML/XML parser or source network resolver is required by this entry.

`assembly.ts` is extracted from the existing Node orchestrator. Both environments use it for canonical root IDs/normalization, profile checks, manifest/resource/attachment declarations, report version 1.0 and validation. Browser identity uses Web Crypto SHA-256 of source bytes, matching Node's existing identity; this is not an authenticity or full-resource-revision claim. Existing Markdown source/resource/options produce identical logical files and diagnostics in both paths. ZIP timestamp equality is not promised.

`@eonhive/prd-packager/browser` exposes `packPackageFiles(files, options)` for in-memory files. It shares `packageSnapshot.ts` with the existing directory writer, including canonical validation, ZIP/envelope selection and final bounded archive-reader checks. Node directory APIs use PRD-049's shared bounded reader and documented coded I/O failures; browser packaging does not import that Node reader. The browser converter uses this existing packager authority; no second manifest or ZIP pipeline is introduced.

The web interface runs conversion in a module Web Worker. File metadata is checked before reading, the bounded supporting-image selection is copied before the first await, resources are read sequentially, and byte buffers are transferred to the worker. Later edits to the caller-owned array cannot replace, append, remove or reorder the validated files while a source or image read is pending. Native File contents remain immutable; the selection snapshot copies references rather than eagerly reading image bytes. Completion transfers the generated archive back; only successful validated conversion enables download and Viewer preview. The parent terminates the worker on success, failure, cancellation, route unmount or a 20-second deadline. It ignores late results. Cancellation during a pending file read prevents further work but cannot abort the already-issued `File.arrayBuffer()` call. This is a responsiveness/deadline boundary, not a hard browser-memory sandbox.

The existing Viewer receives a File built from the completed archive and reuses its ordinary validation/opening/rendering/resource path. Returning to Convert retains the completed archive/report/source excerpt in app memory. File input selections/settings are not persisted across the route remount; choose files again to rerun. Reloading closes that in-memory session. There is no localStorage/IndexedDB upload history or server conversion endpoint. Object URLs are revoked when a result changes or its route unmounts.

## User workflow

1. Open **Convert** from shared navigation.
2. Choose a `.md`, `.markdown`, `.html`, `.htm` or `.cbz` document. Text formats require valid UTF-8 and matching adapter detection; CBZ requires a plain ZIP signature and bounded readable pages.
3. For Markdown/HTML, optionally select PNG/JPEG/GIF/WebP resources referenced by filename, such as `![Description](flow.png)`. Native multi-file selection supports resources in the same virtual directory. CBZ uses archive members instead. A later directory-upload policy can cover nested source folders.
4. Choose automatic or compatible General Document/Comic, an optional title, and whether the exact original source belongs in the output. CBZ also offers natural/reversed filename sequence. Adaptive reading is the only implemented strategy.
5. Convert, review real counts/warnings and download the PRD or quality JSON. **Preview in Viewer** opens the exact result using the reference renderer.

Missing or blocked images receive warnings; unused selected resources are also reported. The output never silently claims those bytes were preserved. Original Markdown is included by default, with its unsupported syntax and potentially private text. Opt-out adds the existing `source-not-preserved` warning. Original-source preview is plain escaped text and does not execute markup. It can remain visible in this local session even when source packaging was disabled.

The source text excerpt and warning list are bounded for UI responsiveness: first 64 Ki UTF-16 code units and first 50 matching warnings, with explicit truncation notices. PRD-056's [quality filters](PRD_CONVERT_QUALITY_REVIEW.md) scan the complete warning list before that display cap. Full conversion still uses the complete bounded source and the downloadable report contains every warning. The current preview is a handoff to Viewer; simultaneous original/converted rendering, general editing, fuller repair queues and recipes remain later increments. Focused CBZ page-order repair is described in the continuation below.

## Limits and resource policy

Browser defaults match the shared reference limits: 4 MiB source, 8 MiB per selected resource, 24 MiB combined selected resources, 128 selected resources and 20,000 output nodes/resource-reference attempts. All selected files, including unused ones, count toward pre-read budgets. The browser API may tighten these limits but cannot increase them. Fixed source-name/resource-path limits are 255/1,024 characters. The API snapshots caller-owned arrays before extraction.

Only explicitly selected relative resource names can resolve. Reject traversal, absolute/drive/scheme/backslash/control/query/fragment paths; percent-decode references once, normalize `.` segments and refuse ambiguous duplicate names. Nested relative keys are available to trusted API callers; the initial UI supplies file basenames only. No filesystem enumeration, adjacent automatic reads, URL crawling or remote image retrieval occurs. The source adapter's existing plain-text/no-HTML semantic mapping is unchanged.

Raster checks are signature/extension screening, not complete pixel decoding or sanitization. Existing Viewer image decoding and native browser memory remain relevant limitations. The worker deadline and byte budgets do not guarantee a maximum process/RSS/GPU allocation. Secure-context Web Crypto, module workers, modern Blob/File/object-URL support and a current browser are required; use HTTPS or localhost. Unsupported worker/crypto environments fail clearly and can use the Node CLI. Conversion code itself sends no source, resource or report to a service; static app/worker asset requests still load normally.
